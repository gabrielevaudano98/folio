# Security

Report vulnerabilities privately through GitHub's "Report a vulnerability" button on the Security tab
(https://github.com/gabrielevaudano98/folio/security/advisories/new), not in a public issue.

Folio's MCP server listens only on 127.0.0.1 and requires a token; AI assistants can reach only the folder open in Folio.
Reports about escaping that folder, bypassing the token, or running code from a document are the most valuable.

## What Folio defends

- **The open folder is the boundary for notes and their assets.** (Exports and the connection setup for AI apps write where you choose or where those apps keep their settings; they are not part of this boundary.) Every read and write of a note by the app or by an AI assistant is resolved against the folder and refused if it leaves it, also through a symbolic link. Hidden files and folders (`.git`, `.env`, `.ssh`) and the folder itself are off limits for changes. A link that stays inside the folder works; a link that leads to a hidden file or folder does not.
- **Notes are untrusted input.** Markdown is sanitised, diagrams run in strict mode, the page has a strict Content Security Policy, and when the app embeds a file or address a note names (in an export), it takes only media from inside the folder or from public internet addresses, checked by name, by what the name resolves to and at every redirect. Web images in a note are not loaded until you ask (per note, or always from Settings); they are then fetched by the app with the same checks, never by the page itself, read in pieces up to 30 MB. The same rule covers pages, the visual editor and slides. A `file:` address written in a note is shown only when it points inside the open folder. **Open** on an attached file hands the system only document and media types from a fixed list: everything else (programs, scripts, shortcuts, installers, macro Office files, unknown types, files with no extension) is refused, so a folder from elsewhere cannot launch code through a link in a note. Template links are fetched with the same public-address checks, at every redirect.
- **The window is locked down.** Only the app page can call the main process, it cannot be navigated elsewhere, and the only browser permissions granted are the microphone (for narration and the meeting recorder) and, while a meeting recording is starting or running, the computer's sound (Windows loopback; the screen picture is dropped at once).
- **Optional components are pinned.** The meeting recorder downloads only what `src/main/features/catalog.js` lists: each file has a fixed address and a SHA-256 checked before use, archives are unpacked in memory with every path checked, and the speech worker is a separate process that runs during a recording and its final transcription. If **Offer to record when a call starts** is on (off by default), the main process reads which apps have the microphone open from the registry (`reg query` on the `CapabilityAccessManager` microphone key, app names and timestamps only) and shows a notification; no sound is captured until the person clicks it and recording starts. The notes engine (llama.cpp's server) runs for one meeting on 127.0.0.1 and is then stopped; its random key is passed on the command line, so it keeps out other users and the network, not programs you already run under your own account.
- **Local server.** The MCP server binds to 127.0.0.1, checks the Host and Origin headers against DNS rebinding, and needs the bearer token, which is stored owner-only. The audience Q&A page is the one deliberate exception: while the presenter has Q&A open it listens on the local network, serves one form, and keeps up to 500 short questions in memory.

## Known limits

- The `RunAsNode` fuse is off on macOS and Linux: the MCP bridge for desktop AI clients runs inside the app binary (`--mcp-stdio`), so `ELECTRON_RUN_AS_NODE` cannot turn it into a Node runtime. On Windows it stays on, because a GUI Electron exe receives no stdin from the program that starts it, so the bridge still runs as Node there. On macOS, clients configured before 1.2.3 keep working through a legacy path; disconnecting and then connecting again rewrites them. Builds are not yet code-signed.
- A web image's address is checked by name and by what it resolves to, then fetched with a second lookup, so a server that changes its answer in between (DNS rebinding) could still reach a private address. Pinning the checked address is planned.
- A change to the folder between the check and the write (a link swapped in at that instant) is not guarded against.
